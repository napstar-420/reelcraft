# ADR-0003: Releases come from release-please, and every release is signed

**Date**: 2026-10-03 (recorded; decided while building the release pipeline, Oct 2026)
**Status**: accepted
**Deciders**: napstar-420, Claude

## Context

Users get Reelcraft as an image and later update it from inside the app. We need versioned releases,
multi-architecture images (Intel/AMD and Apple Silicon), and a way for the in-app updater to trust what it
downloads, without hand-editing versions or changelogs.

## Decision

- **Versions and changelog** are generated by [release-please](https://github.com/googleapis/release-please)
  from conventional commits on `main` (`release-please-config.json`). Versions started at 0.1.0. Merging its
  `chore(main): release X.Y.Z` PR tags the release. Never edit versions or `CHANGELOG.md` by hand.
- **What bumps the version** is decided by the squash-merged PR title: `feat` gives a minor bump; `fix`,
  `perf` and `revert` give a patch bump; a breaking change (`!` or a `BREAKING CHANGE` footer) gives a minor
  bump while below 1.0 (`bump-minor-pre-major`). `chore`, `docs`, `ci`, `test`, `refactor`, `style` and
  `build` don't bump; they ship with the next release.
- **No `develop` branch.** To batch changes, leave the release-please PR open. It only releases when merged.
  If a beta channel is ever wanted, use prerelease tags on `main`.
- **`.github/workflows/release.yml`** does everything in one workflow (tags made with `GITHUB_TOKEN` don't
  trigger other workflows): release-please, then per-architecture `amd64`/`arm64` image builds with the smoke
  test, pushes by digest, a multi-arch manifest (tags `X.Y.Z`, `X.Y`, `X` and `latest`; prereleases only get their exact tag), then release assets and notes.
- **Release assets** are one app bundle per architecture (`reelcraft-app-X.Y.Z-linux-<arch>.tar.gz`, taken
  from the image just built, so an update installs exactly what that image runs), plus
  `reelcraft-X.Y.Z.manifest.json` and its `.sig`. The manifest (`scripts/release/build-manifest.mjs`) lists
  each bundle's size and SHA-256, the image digests, and the `runtime` number from `docker/app/RUNTIME_VERSION`.
- **Signing** is Ed25519 over the exact manifest bytes (`scripts/release/signing.mjs`, shared with the
  updater, `node:crypto` only). The public key is committed (`docker/app/release-signing.pub`) and baked into
  the image. The private key lives only in the `RELEASE_SIGNING_KEY` repository secret. The release
  fails before building anything if signing isn't set up.

## Alternatives Considered

### Alternative 1: Manual tags, version and changelog by hand

- **Why not**: easy to forget and to get wrong, and users can't tell what changed.

### Alternative 2: Unsigned releases, checked by SHA-256 only

- **Why not**: a checksum served from the same place as the file proves nothing if that place is compromised.
  The in-app updater installs new app code into a running container, so the manifest is signed.

## Consequences

### Positive

- Every merge to `main` is releasable at any time, and releases are one click (merge the release PR).
- A tampered bundle or manifest fails verification in the image, which a downloaded update cannot weaken
  (ADR-0004).

### Negative

- PR titles matter: a wrong squash title mis-versions the release.
- Losing `RELEASE_SIGNING_KEY` means existing installs can't verify new releases. Rotating the key needs a new
  image (runtime) release, because the public key lives in the image.

### Risks

- The private key must never pass through an agent session, a commit, or a log. `scripts/release/keygen.mjs`
  prints it once, to the person running it, to put into the secret.
